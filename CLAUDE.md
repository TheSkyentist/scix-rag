# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A local, self-hosted retrieval-augmented-generation pipeline over a citation-graph-selected subset of astro-ph papers (currently seeded from "Little Red Dots" literature via ADS/SciX). The corpus is built by walking the citation graph, then each paper's full text is fetched and cleaned into Markdown. Embedding/retrieval is the active next step (see "Planned next stage" below) — everything through Markdown conversion is built and running in production. The whole pipeline runs locally, by hand, whenever you want to grow the corpus: `pixi run query ...`, then `pixi run all` (= `fetch` → `convert` → `chunk` → `embed`).

This project previously targeted GWDG's hosted Arcana RAG service for embedding/indexing; that integration has been dropped in favor of a fully local pipeline (own embedding model, own vector search) after Arcana's indexing step destructively wiped a previously-working index on a large batch timeout. Don't resurrect `arcana_upload.py`/`ARCANA_*` config or re-introduce an upload-to-Arcana step.

## Commands

Environment/task management is [pixi](https://pixi.sh); each pipeline stage lives in its own pixi feature/environment (separate dependency sets — e.g. the PDF path pulls in `torch` via MinerU, which the HTML-only stages don't need).

```
pixi run all                                     # fetch -> convert -> chunk -> embed in order (run `query` first; stops at the first failing stage; each stage resumes on re-run)
pixi run query --bibcode "2025A&A...702A..57H"   # seed a citation-graph corpus from one paper (ends with the canonicalize pass; --no-canonicalize skips it)
pixi run query --query 'abs:"Little Red Dots"'   # seed from an ADS search instead (many seeds at once)
pixi run fetch [--limit N]                       # fetch raw HTML/PDF for papers not yet converted
pixi run fetch --refresh [--since YEAR] [--dry-run]  # first re-query ADS for papers with no arxiv_id (preprints merged since ingest) and canonicalize them (below); gained ids switch stem, old files dropped once the arXiv copy lands, `chunk` re-chunks them
pixi run canonicalize [--apply] [--since YEAR]   # one row per paper under ADS's canonical bibcode: dry run by default (looks up every paper on ADS, ~2 min)
pixi run convert [--limit N]                     # convert data/html + data/pdf into data/markdown
pixi run convert 1965ApJS....9..321M.pdf         # convert specific file(s), bypassing convert_ignore.txt
pixi run chunk [--limit N] [--rebuild]           # split data/markdown into the `chunks` table (--rebuild drops it and redoes every paper)
pixi run -e embed embed [--limit N] [--model-size 0.6B|4B] # embed pending chunks into `chunk_embeddings` (resumable; Ctrl-C loses ≤ one ~250K-token window)
bin/arxivrag-search {search|chunk|paper|grep|status} ...  # read-only literature search CLI (see "Search" below); also `pixi run search ...`
```

`pixi run query`'s `--no-references`/`--no-citations` flags restrict which side of the citation graph gets pulled (by default both are pulled; citations-only is an option when references mostly reconverge on literature already ingested). All three stages are safe to re-run repeatedly — see "Resumability" below.

There is no test suite, linter, or build step configured in this repo currently.

## Architecture

### Pipeline stages (in order)

1. **`src/ads_query.py`** — queries the ADS/SciX API, builds/updates the citation graph in `data/papers.duckdb`. Two entry points: `build_test_corpus` (one seed bibcode, pulls its direct references + citations — star topology, no cross-links between neighbors) and `build_corpus_from_search` (many seeds from an ADS search query at once, same star-topology logic per seed). Re-running is cheap and safe: only bibcodes not already in the DB get fetched.
2. **`src/fetch.py`** — for every paper in `papers.duckdb` that has no Markdown/HTML/PDF on disk yet, fetches raw content: arXiv HTML5 (then ar5iv fallback) for papers with an `arxiv_id`, otherwise ADS's own hosted PDF sources (tried in `PUB_PDF → ADS_PDF → EPRINT_PDF` priority order, via ADS's link-gateway). HTML is validated by actually running it through the real converter before being kept (falls back to PDF if conversion produces too little text) — but the Markdown from that validation pass is thrown away; `convert.py` owns the copy that's actually kept.
3. **`src/convert.py`** — converts whatever's sitting in `data/html/`/`data/pdf/` into Markdown in `data/markdown/`, deleting the raw file on success. Purely filesystem-driven (no DB reads/writes). HTML path uses `src/html_to_markdown.py` (pure Python, no ML — see below). PDF path shells out to MinerU (`mineru-kit`, standard tier, `--ocr-mode auto` per-page since even nominally born-digital PDFs can have image-only pages) and then strips the references section, base64-embedded figure crops, and ADS watermark lines. Files that convert to fewer than `config.MIN_MARKDOWN_CHARS` are left in place for manual review rather than retried automatically. Filenames listed in `convert_ignore.txt` (repo root, committed; one per line, `#` comments) are skipped by the bulk run — for PDFs that reliably fail/time out — but converted anyway if named explicitly on the command line (or all of them with `--retry-failed`). The bulk run appends to the list itself on MinerU timeout (1800 s), non-zero `mineru-kit` exit, or too-little-text output; explicit targets never record. `fetch.py` doesn't consult the list.
4. **`src/html_to_markdown.py`** — the actual HTML→Markdown cleaning logic `convert.py`'s HTML path calls. Recursively walks LaTeXML's `<section>`/`ltx_para` structure into heading + paragraph blocks, swaps every `<math alttext="...">` for inline/display LaTeX (avoids embedding raw MathML), renders figures as caption-only (images are never embedded, just their captions) and tables as pipe-delimited text, keeps lists (one block per item) and display equations that LaTeXML places beside the `<p>` tags inside an `ltx_para` div (earlier versions silently dropped both, so Markdown converted before this fix lacks them until the raw HTML is re-fetched), and drops the bibliography entirely (the citation graph lives in `citation_edges`, not embedded prose).

### Resumability ("done" tracking)

Deliberately simple, filesystem-first design: a paper is considered fetched/converted once `data/markdown/{stem}.md` (or `data/html/{stem}.html` or `data/pdf/{stem}.pdf`) exists, full stop. `fetch.py`/`convert.py` do not write pipeline-status columns to `papers.duckdb` — the one exception is `esources` (which full-text sources ADS claims to have per paper), which is real ADS metadata worth caching, not pipeline bookkeeping. This trades a small amount of wasted retry effort (an unfetchable paper gets retried every run, no permanent "gave up" marker) for every stage being trivially safe to interrupt and re-run.

The one exception to "no permanent gave-up marker": `fetch.py` appends papers where every source definitively answered "no" to `fetch_ignore.txt` (repo root, committed; `stem  # reason`) and skips them on later runs; `fetch --retry-failed` ignores the list. Network errors/timeouts/429/5xx and failed `esources` lookups are never recorded (they retry next run). `convert.py` does the same for `convert_ignore.txt` (see above).

`stem` is `arxiv_id` when present, else `bibcode` — this is also the filename convention used everywhere under `data/`.

**Identity** (`src/canonicalize.py`): one paper = one `papers` row keyed on ADS's *canonical* bibcode. ADS re-keys records (preprint `2026arXiv…` → journal bibcode, old one becomes an `alternate_bibcode`; a journal record gains an arXiv id), so rows drift into twins and stale `arxiv_id`/`esources`. `canonicalize.run(con, docs, apply)` groups rows that are the same paper (same canonical bibcode after alias resolution, or same arXiv id) and merges each group: one row under the canonical bibcode, `citation_edges` repointed (incl. dangling endpoints that are aliases of known papers; dupes/self-loops dropped), one member's chunks/embeddings re-keyed (no re-embedding; prefers chunks built from the final arXiv stem), old-stem raw files moved/dropped, `fetch_ignore.txt`/`convert_ignore.txt` stems rewritten (a paper with an arxiv_id has its bibcode-stem ignore line dropped so it's retried via arXiv), `evals/search_gold.json` bibcodes updated. `pixi run query` ends with a full-DB pass (`--no-canonicalize` skips it), so twins never accumulate, `fetch --refresh` calls it for papers still lacking an `arxiv_id`, and `pixi run canonicalize` is the same pass as a standalone dry run by default. `chunk` re-chunks a paper whose `chunks.arxiv_id` no longer matches `papers.arxiv_id` (once the new Markdown exists). Applying rewrites keys in `papers.duckdb` (and moves/deletes old-stem files under `data/`); `query` does this automatically.

### Data model (`data/papers.duckdb`)

Two tables:
- **`papers`** — one row per paper, keyed on `bibcode` (ADS's universal ID; not every paper has an `arxiv_id`, e.g. pre-arXiv instrumentation papers, so bibcode has to be the real primary key). `arxiv_id` is nullable and is the actual join key used for on-disk filenames. `alternate_bibcode` absorbs bibcode churn from preprint→published transitions. `query_source` records how a paper entered the corpus and is first-write-wins on upsert (never overwritten on re-query). Upserts refresh everything else (e.g. `citation_count` changes over time).
- **`citation_edges`** — directed `(citing_bibcode, cited_bibcode)` pairs, star topology only (a seed's direct references/citations, not cross-links between neighbors).

`data/papers.duckdb` (and its `.wal`) is deliberately **not** in git (multi-GB; `*.duckdb`/`*.duckdb.wal` are gitignored, and it was purged from history), so back it up outside the repo. `data/html/`, `data/markdown/`, `data/pdf/` are ephemeral local working files, regenerated by re-running `fetch`/`convert`, and are gitignored too.

## Chunking (`src/chunk.py`) + embedding (`src/embed.py`), both built; embedding not yet run on the full corpus

Chunking splits each paper's Markdown into passage-sized chunks in the `chunks` table; `embed.py` embeds them for retrieval (replacing what Arcana used to do internally). Design:

- **Embedding model**: Qwen3-Embedding, run locally with MLX in bf16, size set by `config.EMBED_MODEL_SIZE` (currently `0.6B`, 1024-d; `4B` is 2560-d). The default is a provisional choice, not a settled one. Measured on this M2 Pro (16 GB): 4B ≈ 385 tok/s (≈150 h for the corpus); 0.6B ≈ 3,600 tok/s end-to-end (≈16 h). 8-bit/4-bit were *slower* than bf16 (only saving memory), and 8-bit ≈ bf16 in quality. A retrieval test on the new chunks (25 LRD papers, abstract-sentence → own-paper passages) put 4B only slightly ahead of 0.6B (MRR 0.787 vs 0.754, not distinguishable from zero at 95%); top-10 lists overlap only ~68%. Weights need a hand-built `mlx_lm.models.qwen3.Model` (HF embedding checkpoints lack the `model.` key prefix) with last-token pooling + L2 normalization — `embed.load_embedder`/`embed_texts`. The embed env resolves `transformers` 5.x (via `mlx-lm`) while the chunk env pins 4.57; both tokenize identically.
- **Chunk boundaries**: walk the Markdown's own heading structure, pack consecutive paragraphs within a section up to `config.MAX_CHUNK_TOKENS` (1024), cut only at paragraph boundaries, no overlap between adjacent chunks. A paragraph over budget is split at newlines, then `•` bullets, then sentences, and re-packed. Token counts use Qwen3's own tokenizer, not a proxy.
- **Chunk kinds** (`chunks.kind`): `prose`; `table` (a whole table, or an over-budget numeric/LaTeX data dump — stored in full but only `chunk.table_embed_text()`, caption + header row up to `config.MAX_TABLE_EMBED_TOKENS`, is meant to be embedded); `boilerplate` (acknowledgements, data availability, author contributions, conflicts, funding, leaked reference lists — kept searchable but the embed stage can skip them by default).
- **Embedded-text prefix**: each chunk gets the paper title + its heading path (`chunks.heading_path`, e.g. `2 Method > 2.3 Raman Scattering > 2.3.1 Physical Mechanism`; numbering is kept, it encodes the parent) prepended before embedding (disambiguates otherwise-generic-sounding passages); the prefix is reconstructed at embed time from other columns, not duplicated into stored chunk text.
- **Storage**: two tables in `papers.duckdb`, no separate vector store. `chunks` (`bibcode`, `arxiv_id`, `chunk_index`, `section_heading`, `heading_path`, `kind`, `text`, `n_tokens`) and `chunk_embeddings` (`bibcode`, `chunk_index`, `model`, `text_hash`, `embedding FLOAT[]`). Embeddings are a separate table so several models can coexist and `chunk --rebuild` doesn't silently destroy them. `text_hash` is a hash of the exact embedded string (title + heading path + body): a chunk is pending when it has no row for the model or the hash differs, so re-chunking or changing the prefix (`config.EMBED_TITLE_PREFIX`) re-embeds exactly the affected chunks instead of leaving vectors attached to different text; orphaned rows are deleted on start. Cast with `embedding::FLOAT[1024]` for DuckDB's array/VSS functions. Size: ~334K vectors ≈ 1.4 GB raw for 0.6B (≈3.4 GB for 4B) on top of the ~1.8 GB of papers/chunks; the whole ~4 GB file stays out of git (see above).
- Papers with no Markdown on disk yet (still pending fetch/convert, or in MinerU's PDF queue) are simply skipped at embed time, same skip-if-not-ready pattern the rest of the pipeline already uses.

## Search (`src/search.py`, `bin/arxivrag-search`)

A read-only CLI plus a Claude Code Skill, meant for infrequent single-user queries from any project (no server, no warm cache by design). Subcommands: `search` (semantic; 1–4 query variants embedded in one model load, fused by reciprocal rank, per-paper cap; optional repeatable `--term REGEX` — see "Fused search" below), `chunk BIBCODE#INDEX --context N`, `paper BIBCODE [--chunks A-B | --full]` (outline by default; text is rebuilt from `chunks`, not the ephemeral `data/markdown/`), `grep` (exhaustive, unranked literal/regex over chunk text incl. boilerplate; `--word --case --since --also REGEX`; for complete paper lists, exact IDs/numbers/claim checks, and testing a regex), `status`.

- **Scoring is done inside DuckDB** with the core `list_inner_product(embedding, ?::FLOAT[])` on the stored `FLOAT[]` column (vectors are unit length, so it equals cosine; no `vss` extension needed). The scoring query touches only `chunk_embeddings` (filters like `--since` sit inside the scan, before the top-N); `chunks`/`papers` are read only for the final hits. Never pull vectors into Python (`fetchall` on list columns is very slow). Queries are formatted `Instruct: {config.QUERY_INSTRUCTION}\nQuery:{q}` (`embed.format_query`); documents have no instruction.
- **No `.env` needed**: `config.ADS_API_KEY` is optional at import; only `ads_query` raises (clearly) when it is missing.
- **Pixi env**: search shares the `embed` environment (it needs `mlx` to embed the query); `search` and `embed` are both tasks of the `embed` feature. `bin/arxivrag-search` runs `.pixi/envs/embed/bin/python` directly (no pixi startup), so it is unaffected by a running `embed` job. Don't pin `transformers` in the `embed` feature (`mlx-lm` needs ≥5; the `chunk` env pins <5).
- `embed.load_embedder(size, offline_first=True)` loads from the local HF cache without the Hub's online revision check (falls back to download if not cached).
- **Fused search (`search --term`)**: Claude supplies regexes (RE2, case-insensitive; repeat = OR; `(?-i:…)` for exact case). One regex scan of `chunks` (non-boilerplate text + heading path, `--since` inside the scan) picks the matching chunks and computes their cosine to *every* query variant in one pass (`_term_scan`); those term-restricted rankings are added as extra lists to the same reciprocal-rank fusion (`TERM_WEIGHT`, 1.0; sweeping 0.25–1.0 on the gold set showed no gain from lowering it). Output: `+term` tags, keyword-in-context previews (matches in **bold**, windows joined by `[…]`) when the match lies beyond the clipped head, and a "other papers matching the term" list ordered by matching-chunk count (`--papers N`, default 25, max 300, 0 = off). Zero matches / more than `TERM_TOO_GENERIC` chunks print warnings; bad regexes fail with an RE2 hint. Without `--term` behaviour is unchanged. Gold-set check: `.pixi/envs/embed/bin/python -m evals.run_search_eval` (`evals/search_gold.json`; "provisional" cases are partial lists that need curation, and term-only recall is partly circular because gold was found with grep). Measured so far: fusion lifts top-k recall modestly (13/26 → 16/26 gold papers), the listing is what delivers coverage (26/26), and fusion can drop a semantically good paper that lacks the term (Balmer case), which the listing recovers.
- `chunk --rebuild` tags leaked front matter headings (authors, affiliations, ORCIDs, keywords) as `boilerplate`; `embed` drops the vectors of chunks that became boilerplate (this model only) before counting what is pending, so a re-tag needs only `chunk --rebuild` then `embed`. `search status` reports not-yet-dropped ones.
- The DB is opened `read_only=True`; while `embed`/`chunk` hold the write lock it fails with a one-line message (exit 2). Run `embed` after `chunk --rebuild`, or embeddings may be stale/orphaned (`status` counts orphans).
- The Skill's source is `skills/arxivrag-search/SKILL.md` (symlinked into `~/.claude/skills/`).
